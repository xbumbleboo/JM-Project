# Technical Documentation — JM Synthetic Data

> **Synthetic data.** All data in this project was generated by the author in Python, based on JM's public scale, policies, prices and promotions. These are not JM's real figures and do not reflect JM's actual business performance.

*Version 08/11/2026 · Python (generator, CLV model) · Google BigQuery, GoogleSQL · Power BI Desktop, DAX · Companion to [#3 Insight Report](insight-report.md) and [#8 Synthetic Data Design](synthetic-data-design.md)*

**Scope.** [#8](synthetic-data-design.md) covers the path from business rules to the 18 tables produced by the generator. This document covers the next step: from those tables into BigQuery, through the view layers, to the Power BI model. It also describes how every number on the dashboard is checked against BigQuery.

**Summary**

- Data passes through four layers: source tables → per-channel staging → shared fact views → dashboard-specific views. Each metric is defined once, in the shared layer, and never redefined in individual reports.
- Power BI loads 7 `pbi_*` views into a star schema. The Year and Month slicers are disconnected tables; every measure goes through a shared set of time templates.
- Every view has check figures run on BigQuery. Every dashboard page was reconciled against BigQuery before sign-off.

The dashboard and the model are built in Vietnamese, so table, column and measure names below are kept in Vietnamese, with English descriptions.

## 1. Data architecture

| Layer | Objects in BigQuery | Role |
|---|---|---|
| Source | `bills_raw`<br>`orders_raw`<br>`depots`<br>`nhanh_products_full`<br>`nhanh_categories`<br>`nhanh_internal_categories` | 6 tables from the generator, in the Nhanh.vn structure, loaded with `WRITE_TRUNCATE` |
| Derived source | `customer_analytic_base`<br>`customer_clv`<br>`dim_platform_fee` | Physical tables, computed once and reused:<br>one row per customer (two-channel RFM, card tier, segment)<br>CLV model output<br>marketplace fees by effective date range |
| Staging | `stg_offline_revenue`<br>`stg_online_revenue` | One view per channel: status filters, consistent column names |
| Shared facts | `fct_retail_revenue`<br>`fct_product_revenue` | Define revenue (per transaction) and sales (per line item) for both channels |
| Analysis layer | `fct_offline_bill`<br>`fct_online_order`<br>`dim_diem_ban`<br>`dim_product`<br>`dim_price_band` | Used during the analysis phase before the dashboard was built; not used by the dashboard |
| Dashboard layer | `pbi_giao_dich`<br>`pbi_dong_hang`<br>`pbi_don_online`<br>`pbi_ngay_mua`<br>`pbi_dim_diem_ban`<br>`pbi_dim_san_pham`<br>`pbi_dim_khach` | Each view matches the grain of one table in Power BI |

**From the generator to BigQuery.** The generator writes 18 tables. The analysis keeps 6 of them as sources. The two customer tables `nhanh_customers_full` and `t_customer_tier_final` were used once to build `customer_analytic_base`; all customer analysis reads from that table afterwards. The other 10 tables are not used; the reason for each is in [#8](synthetic-data-design.md), sections [2.2](synthetic-data-design.md#22-tables) and [6](synthetic-data-design.md#6-data-limitations). BigQuery currently holds 9 tables and 16 views.

**Why the dashboard reads from `pbi_*` views** rather than queries written inside Power BI:

- One view serves several pages and is fixed in one place.
- Check figures run directly on BigQuery, without opening Power BI.
- The lineage of every number can be read end to end: source → stg → fct → pbi.

Four small static tables (waterfall, dead SKUs, promotion calendar, uplift; 3–27 rows) are entered directly in Power BI because they are finalised analysis results that do not need recomputing.

## 2. Shared metric definitions

| Metric | Definition | Source and filters |
|---|---|---|
| Offline revenue | Sales invoice amounts, plus exchange fees on return slips | `fct_retail_revenue` |
| Online revenue | Amount the business receives (`business_payment`) on delivered orders | `fct_retail_revenue`. Excludes "Khách trả lại hàng" (customer return) rows |
| Transactions | Each row of `fct_retail_revenue`: sales invoices, offline return slips, delivered online orders | `fct_retail_revenue` |
| Sales | Price × quantity − discount, per line item, before returns | `fct_product_revenue`. Offline sales invoices and "Giao hàng tận nhà" (home delivery) orders only |
| Regular sales | Online line items, or offline line items on invoices that did not redeem points | Denominator for gross margin and discount rate, because invoices that redeem points record zero discount |
| Tier at purchase | Derived from points earned per VND 100k on the sales invoice: 1, 2, 3, 5, 8 map to the 5 card tiers | `pbi_giao_dich` |
| Identified customers | Excludes the 3 shared accounts (id 1, 2, 3) | All customer-level analysis |
| Cancellation, return-to-sender rate | Orders in the group ÷ orders placed | `pbi_don_online` |
| Post-delivery return rate | Orders with a return slip ÷ delivered orders | `pbi_don_online`. Different denominator from the two rates above |

The three ways an online order can fail are kept separate, each with its own denominator, and never added into a single rate.

**Two numbers that differ because their definitions differ.** On the Offline page, the card-tier donut totals VND 149.9bn while the offline revenue KPI shows VND 150.2bn (Jan–Aug 2026). The donut counts only sales invoices with a known tier, because a card tier belongs to a purchase. The KPI counts every document. Both are correct. The VND 275m gap is the exchange fees on return slips (VND 269m) plus sales invoices under VND 100k, whose tier cannot be derived (VND 6m).

The data is small (the largest table is about 1.1 million rows) and does not change, so the model uses **Import mode**. All relationships are one-to-many and single-direction: dimensions filter facts.

**The Year and Month slicers are not related to any table.** Monthly charts must keep all three years and the full Jan–Dec axis when the viewer selects a year or a month. If the slicers filtered the `Date` table directly, the charts would lose the other years and months. The slicers are therefore read only inside measures, through 7 shared templates:

| Template | Returns |
|---|---|
| A · period | Value for the selected year and months; with no year selected, the latest year with data for those months (2026, or 2025 if only Sep–Dec is selected) |
| B · prior year | Same period of the previous year, limited to the months that have data in the year being viewed |
| C · YoY | Change against the same period of the previous year |
| D · MoM | Change of the last selected month against the month before |
| E · period label | Title suffix: `2025`, `T1–T8/2026`, `T3–T5/2025` (T = month) |
| F · comparison line | Sub-line under a KPI value, with ▲/▼ coloured by whether the change is good or bad for the business |
| G · monthly chart | The Online page monthly chart shows only the viewed year and the prior year |

Template A applies the selected year and months to the `Date` table:

```DAX
X · kỳ =
VAR y = [_Năm]                              -- year being viewed
VAR ThangChon = VALUES ( SL_Thang[Tháng] )  -- selected months; none selected = all 12
RETURN
    CALCULATE ( [X], 'Date'[Năm] = y, TREATAS ( ThangChon, 'Date'[Tháng] ) )
```

Template B keeps YoY a like-for-like comparison. 2026 has data up to August, so Jan–Aug 2026 is compared with Jan–Aug 2025, not with the whole of 2025:

```DAX
X · năm trước =
VAR y = [_Năm]
VAR ThangChon = VALUES ( SL_Thang[Tháng] )
VAR ThangCoDuLieu =                         -- selected months that have data in year y
    CALCULATETABLE ( VALUES ( 'Date'[Tháng] ), REMOVEFILTERS ( 'Date' ),
        'Date'[Năm] = y, 'Date'[Có dữ liệu] = TRUE (), TREATAS ( ThangChon, 'Date'[Tháng] ) )
RETURN
    IF ( y - 1 >= 2024,
         CALCULATE ( [X], 'Date'[Năm] = y - 1, TREATAS ( ThangCoDuLieu, 'Date'[Tháng] ) ) )
```

Every measure on the dashboard combines one template with one base measure (e.g. `[Doanh thu]`, revenue). All measures live in the `.pbix` file, organised in folders for templates, base measures, period measures, and labels and colours.

## 4. Reconciliation

### 4.1 Three levels of checks

A mismatch at any level stops the work at that level.

1. **Every view has check figures** run on BigQuery before it is loaded into Power BI: row count, revenue totals by period, nulls in key columns. For example, `pbi_giao_dich` has 826,943 rows, Jan–Aug 2026 revenue of VND 203,716,541,898 and full-year 2025 revenue of VND 347,528,780,193.
2. **Numbers must add up to each other.** For example, the two steps of the 2025 waterfall (change due to the number of transactions and change due to value per transaction) add up exactly to Jan–Aug 2025 revenue: 189,857,630,120 + 17,998,780,358 = VND 207,856,410,478.
3. **Every dashboard page** in its default state (Jan–Aug 2026) is reconciled against BigQuery. Three more states are then tested: 2024 selected (no prior year), 2025 selected (full year), and March selected with no year (must show March 2026, MoM against February 2026).

### 4.2 Three silent query errors and how they are blocked

The three errors below do not make a query fail; they only make the numbers wrong. Each was caught by one of the checks in 4.1 and is blocked by a rule applied to every query afterwards.

| Error | Caught by | Blocking rule |
|---|---|---|
| Joining on `order_id` duplicates rows | Comparing `COUNT(*)` with `COUNT(DISTINCT order_id)`: 417,981 rows but 384,873 order IDs. Online return slips reuse the original order's ID | The key of `orders_raw` is `(order_id, order_type)`; every join includes `order_type` |
| Online sales overstated by 11.1% | Rebuilding sales with both filter methods and comparing | Online return rows also carry a product list. The line-item table filters by document type in both the offline and online branches, rather than relying only on a list of valid order IDs |
| A view change alters published numbers | Rebuilding the old number in the same query (adding back the excluded rows) | Numbers on the dashboard are replaced only when the gap can be explained exactly |
